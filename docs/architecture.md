# 架构与边界

LabKB 的目标是把课题组资料变成可以追溯的问答入口，并用同一份题库比较模型和机器。资料导入后参与检索，不会自动训练或微调模型。

## 从资料到回答

1. 解析 TXT、Markdown、PDF、DOCX 的文字，并把长文档切成相互有重叠的片段。PDF 只处理已有文字层，表格与复杂排版可能丢失语义。
2. 将文档元数据和片段存入本地 SQLite。Ollama 模式还调用 `/api/embed` 得到文档向量。
3. 接收问题和有限的会话历史，进行关键词检索；Ollama 模式增加查询向量和语义相似度检索，再融合候选排序。
4. 将检索到的证据片段编号，交给聊天模型。资料是证据，不应作为可执行指令。
5. 返回回答与来源片段；没有检索证据时拒答。demo 模式直接返回相关摘录。

Ollama 官方将嵌入用于语义检索，要求索引与查询使用相同的嵌入模型；嵌入服务与聊天服务可以采用不同模型。[官方嵌入文档](https://docs.ollama.com/capabilities/embeddings)

## 为什么先选这个栈

| 层 | 当前实现 | 选择原因与边界 |
| --- | --- | --- |
| 网页与 API | FastAPI + 项目自带静态页面 | 单进程容易运行，适合研究原型 |
| 文档解析 | pypdf、python-docx、文本读取 | 无需把文档传到外部解析平台；未包含 OCR |
| 资料存储 | SQLite | 无需单独数据库服务；适合本机小规模试验 |
| 检索 | 关键词排名 + 本地向量相似度 | 中文术语和语义问题可以分别检查；未包含重排序模型 |
| 模型连接 | httpx → Ollama | 可替换模型标签；需自己测量显存与吞吐 |
| 数据访问 | 单个共享知识库 + 可选共享令牌 | 令牌控制进入系统，不能隔离不同用户的文档 |

向量目前在应用内进行遍历检索，数据量增加时耗时和内存需求都会增长。不要把这一原型包装成“百万文档开箱即用”。先记录片段量、检索延迟和内存；达到目标机器的容量边界后再评估专用向量数据库、后台导入任务和服务拆分。

当前限制为单文件 10 MiB、提取文字 50 万字符、PDF 300 页、全库 5000 个片段。导入、检索和生成采用单进程锁保护，长时间生成会使其它知识库操作等待。此设计便于保持删除与回答的一致性，不适合直接增加 Uvicorn workers；多进程需要重新设计操作协调和容量保护。

索引记录模式、分块参数、嵌入模型名称及其 Ollama 模型摘要。配置或嵌入模型内容改变时，系统拒绝混用旧索引；使用新的数据目录重新导入，或明确删除全部文档后重新建立索引。只比较聊天模型时不需要改变嵌入索引。

## “上下文断了”不只与显存有关

需要分别排查：历史是否传入、历史是否截断、指代是否明确、关键证据是否检索到、提示长度是否超预算、模型本身是否理解问题。提高显存或增大窗口不能自动修复以上问题。

当前历史长度受限，不是无限记忆；检索也不是完整的对话查询改写器。对于“那它呢”这类省略表达，评测应包含明确的多轮案例。无法恢复指代时，回答应说明资料或上下文不足。上下文应给证据和生成留出空间；模型、嵌入以及并发都竞争机器资源。

## 数据流与信任边界

默认 demo 不发出模型请求；Ollama 模式将检索问题、相关历史和文档片段发送到配置的 `LABKB_OLLAMA_URL`。保持该地址指向受控的本地服务、使用本地下载的模型，才符合本地处理的部署目标。配置为远程服务时，相应数据会离开本机。

模型输出可能包含错误，片段中的恶意文本也可能影响回答。系统不提供模型工具执行、网页代理或自动执行文档命令；但提示词与引用机制不能保证完全消除提示注入。实验参数、仪器操作和安全规定以有效版本的原始资料为准。

## 可扩展方向

以下是后续候选工作，不属于当前已完成能力：

- 按项目和人员控制文档可见性，并让检索严格遵守相同权限。
- 文档版本管理、审核发布、过期提醒和可追溯审计。
- OCR、结构化表格解析、图片与公式检索。
- 查询改写、重排序、流式回答和中断。
- 基于实际瓶颈引入向量索引、后台导入任务、队列和并发限制。

这些扩展需要对应测试与验收，不能仅通过切换一个模型标签获得。
