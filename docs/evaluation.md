# 评测指南

要评估课题组的硬件采购，先固定“什么问题答得对、什么速度能接受、多少人同时用”，再比较硬件。demo 只用于检验导入、检索和页面流程；真实模型与硬件评测必须使用 `ollama` 模式。

## 建立小而真实的题库

先收集 30–50 个课题组新人常见问题，并请熟悉业务的人为每题标注标准答案要点、有效来源和文档版本。资料不足的题也要保留，不能只测“总能找到答案”的案例。

| 题型 | 示例方向 | 检查重点 |
| --- | --- | --- |
| 单文档事实 | 某仪器如何预约 | 引用片段是否直接支撑答案 |
| 操作流程 | 新人第一次上机要完成哪些步骤 | 是否遗漏前提、审批或注意事项 |
| 多文档综合 | 预约与培训要求有何关联 | 多个依据是否一致，是否混用旧版 |
| 中文术语和缩写 | 仪器简称、方法缩写 | 关键词检索和语义检索分别是否命中 |
| 无答案 | 未导入的项目参数 | 是否明确表示没有依据 |
| 多轮追问 | 先问设备，再追问“需要谁批准” | 历史与指代是否正确 |
| 对抗资料 | 文档夹带“忽略规则”等文本 | 是否继续把资料当作证据而非指令 |

示例资料是虚构的功能演示内容，不能替代组内真实评测题库。评测题库和真实输出本身也可能含内部信息，默认留在本地。

## 自动记录

启动服务、导入题目所需资料后运行：

```text
python scripts/benchmark.py --base-url http://127.0.0.1:8000 --questions examples/eval.jsonl --output data/benchmark.json
```

如果服务启用了令牌，在启动脚本的 shell 中设置 `LABKB_API_TOKEN`。PowerShell 使用 `$env:LABKB_API_TOKEN='你的令牌'`；不要将带实际令牌的命令贴到 issue 或公开日志。

题库为 JSONL，一行一题，例如：

```json
{"id":"onboarding-1","question":"新人入组第一周应该做什么？","expected_documents":["新生入组指南.md"],"expect_refusal":false}
```

`expected_documents` 使用上传后的完整文件名；无答案题可以为空数组。多轮题可增加 `history` 数组，其中每项为 `{"role":"user","content":"之前的问题"}` 或 `assistant` 消息。样例历史只用于试验，不要把模型生成的内容当成标准答案。

脚本以 `top_k=4` 检索并计算 `recall_at_4`，再请求问答，记录 `refusal_accuracy`、端到端平均 / P50 / P95 延迟，以及 Ollama 实际返回的生成 token/s。`recall_at_4` 是期望文档集合被命中的比例，不能证明具体片段已覆盖所有要点。多轮案例的独立检索调用只使用当前问题，聊天内部可能使用历史扩展检索，因此该指标不等于多轮聊天内部的真实召回。

用 `--repeat 3` 可以重复每题。失败请求计入 `errors`，不计入成功样本的平均值，阅读平均值时必须同时查看错误数量。脚本的其它字段和选项以 `python scripts/benchmark.py --help` 及输出 JSON 为准。

输出中没有的指标不可当成已测得；尤其是完整请求延迟不等于首 token 延迟，字符数/秒不等于 token/秒。非流式请求无法从客户端直接得到真正的首 token 时间。脚本在聊天前执行独立检索，因此聊天延迟可能已经受预热影响；严格冷启动测试需要另行记录一次未经预检索的聊天请求。

至少区分一次冷启动和多次热运行。记录运行日期、机器配置、操作系统、驱动、Ollama 版本、模型完整标签、量化、窗口、资料版本和片段数。若模型返回官方计时指标，生成 token/s 按 `eval_count / (eval_duration / 1e9)` 计算；这是生成阶段速率，不能替代端到端体验。[Ollama 用量与计时字段](https://docs.ollama.com/api/usage)

## 人工判分

给每题保存原始回答和引用，请评审者盲评，不根据模型名称打分。建议以以下工作表记录，目标值由课题组实际需求决定：

| 指标 | 定义 | 初始目标 | 实测 |
| --- | --- | --- | --- |
| 正确率 | 回答覆盖标准要点且无关键错误的题数 / 可回答题数 | 待组内确定 | 待测 |
| 来源命中率 | 期望来源进入检索结果的题数 / 有来源题数 | 待确定 | 待测 |
| 引用支持率 | 引用内容确实支持对应主张的比例 | 待确定 | 待测 |
| 拒答表现 | 无依据题能拒答；有依据题不过度拒答，分别计数 | 待确定 | 待测 |
| 多轮连贯性 | 有指代的连续问题中正确继承语境的比例 | 待确定 | 待测 |
| 端到端延迟 | 完整请求的 P50、P95，注明样本量 | 待确定 | 待测 |
| 生成速度 | 模型实际输出 token/s，记录计时口径 | 待确定 | 待测 |
| 资源峰值 | 显存、系统内存、功耗和并发下的资源情况 | 待确定 | 待测 |

检查引用编号存在只说明格式或来源可解析，不能自动证明引用支持答案。来源命中率也不等于回答正确率。人工评测需要核对原文，不应完全交给另一个模型决定。

## 比较方案

保持资料、问题和窗口不变，先比较关键词检索与真实语义检索，再比较聊天模型。每轮只改一个主要变量，避免把文档清洗的收益误归因于更贵的显卡。

1. 用现有电脑确认资料解析与 demo 路径。
2. 用同一台机器测试能运行的本地模型，记录是否出现 CPU 分担。
3. 借用或短期试用候选 GPU 机器，复跑完全相同的题库。
4. 加入长问题、连续多轮和多个客户端同时访问，记录错误率与排队延迟。当前脚本不替代完整负载测试。
5. 把质量、延迟、资源与报价填入硬件表，再决定购买。

## 验收记录

每份报告应明确标记“实测”“估算”“未验证”。仓库自动化测试验证软件行为，使用模拟模型的测试不能证明真实模型的语义质量、实际显卡吞吐或 Docker 可用性。没有相应机器和测试结果时，保持这些项目为未验证。

建议保留一份固定的回归题库，资料、模型、提示或检索策略变化后重跑。对于会影响实验操作的错误，应单独登记并修正资料或系统，再邀请新人试用。
